# Secrets Management

A secret is any value that grants access to a system: database passwords, API keys, TLS private keys, OAuth tokens, SSH keys, encryption keys. **Secrets sprawl** — the proliferation of secrets across codebases, CI/CD systems, container images, and configuration files — is one of the most pervasive and underestimated security problems in modern engineering.

<Callout kind="danger">
**Git history never forgets.** A secret committed to a repository remains in git history even after deletion. It is cloneable by anyone with repository access — or publicly searchable on GitHub if the repository was ever public. Assume any secret committed to git is permanently compromised.
</Callout>

---

## Where Secrets Leak

### Source Code

The most common and most dangerous location. Developers hardcode credentials for convenience during development, intending to "fix it later." Later rarely comes.

```python
# Hardcoded credentials — visible to every developer, in every git clone
DB_PASSWORD = "production_password_123!"
stripe.api_key = "sk_live_4xFqN9AbcD..."

# GitHub's secret scanning detects known patterns automatically,
# but only after they've been pushed. Prevention is better.
```

### Environment Variables

Environment variables are better than hardcoded values but have their own risks:

- Visible to all processes running as the same user
- Logged by `printenv`, `ps auxe`, error reporters (Sentry captures `os.environ` on unhandled exceptions)
- Exposed in Kubernetes pod specs (`env:` fields visible in `kubectl get pod -o yaml`)
- Passed to child processes without explicit opt-out

### Dockerfile ARG and Image History

```dockerfile
ARG DATABASE_URL=postgres://admin:password@prod/db
# This is visible via:
# docker history <image>
# docker inspect <image>
# Any registry the image is pushed to
```

BuildKit secret mounts solve this cleanly — secrets are mounted at build time and never stored in any layer.

### CI/CD Pipelines

CI secrets are often over-shared: a single `AWS_ACCESS_KEY_ID` used across all pipelines has access to everything. If the CI system is compromised or a malicious dependency exfiltrates the environment, all secrets are gone.

### Kubernetes Secrets

Kubernetes Secrets are **base64-encoded, not encrypted**. By default, they are stored in plaintext in etcd.

```bash
# Base64 is not security — decode in one command:
echo "c3VwZXJzZWNyZXQ=" | base64 -d
# supersecret
```

Any user or service account that can `get` or `list` secrets in a namespace has access to all secret values. etcd itself must be encrypted at rest (via `--encryption-provider-config`), and access to etcd nodes must be heavily restricted.

## Secret Detection Tools

Run these in pre-commit hooks and CI to catch secrets before they reach the repository:

| Tool | Notes |
|---|---|
| **gitleaks** | Fast, configurable TOML rules; detects 100+ secret patterns; CI integration |
| **truffleHog** | Scans git history including deleted commits; high-entropy detection |
| **git-secrets** | Simple regex-based; hooks into git commit |
| **Semgrep** | Custom rules for organization-specific secret formats |
| **GitHub secret scanning** | Automatic on public repos; enterprise feature for private |

```bash
# Pre-commit hook using gitleaks
gitleaks protect --staged --redact

# Scan entire repository history
gitleaks detect --source . --report-path gitleaks-report.json
```

## Secrets Management Solutions

### HashiCorp Vault

Vault is the industry standard for centralized secret management. Key features:

- **Dynamic secrets**: Generate short-lived credentials on demand rather than storing long-lived static ones. A Vault database secret engine creates a temporary PostgreSQL user valid for 1 hour, then automatically revokes it.
- **Secret leasing**: Every secret has a TTL. Leaked credentials expire automatically.
- **Audit log**: Every secret access is logged with the requesting identity.
- **Auth methods**: OIDC, AWS IAM, Kubernetes service accounts — no long-lived Vault tokens required.

```bash
# Dynamic database credential — no static password stored anywhere
vault read database/creds/my-role
# Key                Value
# lease_duration     1h
# username           v-token-myapp-AbcDef12
# password           A1b2C3d4-generated-password
```

### AWS Secrets Manager

Managed secret storage with automatic rotation. Integrates with RDS to rotate database credentials automatically without application changes. Supports Lambda-based rotation for other secret types.

```python
import boto3

def get_secret(secret_name):
    client = boto3.client("secretsmanager")
    response = client.get_secret_value(SecretId=secret_name)
    return response["SecretString"]
```

### Kubernetes + External Secrets Operator

External Secrets Operator syncs secrets from Vault, AWS Secrets Manager, or GCP Secret Manager into Kubernetes Secrets. Applications read from Kubernetes Secrets (native integration), but the secret values live in a managed backend — not in etcd or git.

## Secret Rotation

Static credentials that never change accumulate risk: they are copied across machines, logged, and forgotten. Rotation limits the window of exposure.

**Rotation strategy**:
1. Generate new credential
2. Update the secret in the secrets manager
3. Rolling deploy of application (reads new credential from secrets manager)
4. Revoke the old credential after a grace period

Vault's dynamic secrets make rotation implicit — there is no static credential to rotate because every credential is already short-lived.

---

## Responding to a Leaked Secret

1. **Revoke immediately** — do not wait to investigate. Revoke the credential before doing anything else.
2. **Rotate** — generate a new credential and deploy it.
3. **Audit access logs** — determine what was accessed using the compromised credential and during what time window.
4. **Check downstream systems** — if the leaked credential had access to other services, those systems may also be compromised.
5. **Remove from history** — use `git filter-repo` or `BFG Repo Cleaner` to remove the secret from git history, then force-push. If the repository was ever public, assume the secret was already scraped.

## Misconception

**Myth:** "We store secrets in environment variables, not in code — that's the secure way to do it."

**Reality:** Environment variables are a significant improvement over hardcoded values, but they are not a secrets management solution. They're visible to all child processes, easy to accidentally log, and persist in container spec definitions. The secure pattern is: secrets live in a purpose-built store (Vault, Secrets Manager, Key Vault), applications fetch them at startup or access them via a sidecar, and the fetched values have a short TTL. Environment variables become a *delivery mechanism*, not a *storage location*.
