# Authentication & Session Management

Authentication verifies identity. Session management maintains that identity across requests. Together they're the front door of your application — and the most attacked surface.

For every application, three questions define the auth system: how do users prove who they are, how does the server remember them between requests, and how does the session end when they log out or stay idle?

<Callout kind="insight">
**Authentication answers "who are you?"; session management answers "are you still the same person?"** The classic mistake is conflating the two — and the most common slip is forgetting to regenerate the session ID on login (session fixation). Mark cookies `HttpOnly`, `Secure`, `SameSite=Lax` by default, and treat every privilege change as a reason to rotate the session.
</Callout>

## Authentication Factors

Three categories of proof:

| Factor | Examples | Properties |
|--------|----------|------------|
| Something you know | Password, PIN, security question | Shareable, guessable, forgettable |
| Something you have | Phone (SMS), hardware key (YubiKey), TOTP app | Stealable, losable |
| Something you are | Fingerprint, face, voice | Non-transferable, revocable with difficulty |

**Multi-factor authentication (MFA)** requires two different factor types. Password + SMS is MFA. Password + security question is not (both are "something you know").

**Passwordless authentication** — magic links, WebAuthn (hardware keys), passkeys — eliminates the password entirely. The user proves identity via email ownership or cryptographic challenge. This eliminates credential stuffing, phishing, and password reuse attacks.

---

## Password Storage

Never store passwords in plaintext. Hash them with bcrypt, scrypt, or Argon2. (See Chapter 2 for the crypto details.)

**Additional password practices:**
- **Rate limiting:** 5 failed attempts per account → lockout or exponential backoff
- **Breached password check:** Compare against Have I Been Pwned API on registration and login
- **Length over complexity:** "correct horse battery staple" (44 bits entropy) beats "P@ssw0rd!" (28 bits)

## Session Management

HTTP is stateless. Sessions create state on top.

### Server-Side Sessions

The server stores session data (user ID, roles, expiry). The client holds an opaque session ID in a cookie.

```
POST /login → server validates credentials → creates session {id, userId, expires}
             → sets cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
GET /dashboard → browser sends cookie → server looks up session → identifies user
```

**Session ID requirements:**
- Generated by `crypto.randomBytes(32)` — at least 128 bits of entropy
- Never sequential (no `session_1`, `session_2`)
- `HttpOnly` — JavaScript cannot read it
- `Secure` — only sent over HTTPS
- `SameSite=Lax` — CSRF protection

### Token-Based (JWT) Sessions

The server encodes user data into a signed JSON Web Token. The client stores the token and sends it on every request. The server verifies the signature — no database lookup needed.

**JWT structure:**
```
Header.Payload.Signature
```

**Header:** `{"alg": "HS256", "typ": "JWT"}` — signing algorithm

**Payload:** `{"sub": "123", "name": "Alice", "iat": 1715100000, "exp": 1715186400}` — claims (user data, timestamps)

**Signature:** `HMAC-SHA256(Header.Payload, secret)` — proves the token hasn't been tampered with

**JWT benefits:** Stateless — no server-side session store. The token is self-contained.

**JWT risks:**
- **Cannot revoke individual tokens.** If a JWT is stolen, the attacker has access until the token expires. No session invalidation.
- **Token size.** JWTs can grow large (header + claims + signature). Every request includes the full token.
- **Algorithm confusion.** If the server accepts `alg: "none"`, an attacker strips the signature and the server accepts the token as valid. Always whitelist allowed algorithms.
- **Secret management.** HS256 uses a shared secret. If the secret leaks, the attacker can forge valid tokens. RS256 (public/private key) is safer for distributed systems — only the auth service holds the private key.

### Choosing Sessions vs JWT

| Criterion | Server-Side Sessions | JWT |
|-----------|---------------------|-----|
| Revocation | Immediate (delete session) | Only via expiry or token blocklist |
| Scalability | Requires shared session store (Redis) | Stateless — no central store |
| Data exposure | Server holds all data | Token contains data (don't put secrets in payload) |
| Complexity | Simpler | More pitfalls (alg confusion, key rotation) |
| Recommendation | Default choice | Use for service-to-service, mobile, or when statelessness is required |

## Session Fixation

An attacker forces a victim to use a known session ID.

**How it works:**
1. Attacker obtains a valid session ID (logs in or gets an anonymous session)
2. Attacker tricks the victim into using that session ID (via cookie injection, URL parameter: `?sessionid=KNOWN_ID`)
3. Victim logs in — the server associates the known session ID with the victim's identity
4. Attacker uses the same session ID and is now authenticated as the victim

**Defense:** Regenerate the session ID on login. Always.

```javascript
// On successful login
req.session.regenerate(() => {
  req.session.userId = user.id;
  // Old session ID is invalidated
});
```

**Also regenerate on:**
- Privilege escalation (user becomes admin)
- Logout (destroy old session)
- After a fixed time interval (rotate session ID every 15 minutes for sensitive applications)

## Common Vulnerabilities

### Broken Authentication (OWASP A07)

- **Credential stuffing:** Automated login attempts using breached credentials from other sites
- **Weak password policy:** Accepting "password" or "123456"
- **No rate limiting:** Unlimited login attempts
- **User enumeration:** Different error messages for "user not found" vs "wrong password" — attackers can enumerate valid usernames
- **Insecure password recovery:** Security questions with guessable answers ("What's your mother's maiden name?" — available on Facebook)

### Session Management Failures

- **Session not invalidated on logout:** Server deletes the cookie but doesn't invalidate the server-side session
- **No absolute timeout:** Sessions last forever
- **No idle timeout:** Sessions stay active even if the user hasn't made a request in hours
- **Session IDs in URLs:** Leaked in browser history, Referer headers, and server logs
- **Concurrent sessions:** No limit on simultaneous sessions per user

## Best Practices

| Practice | Implementation |
|----------|---------------|
| Password storage | bcrypt with cost factor ≥ 12 |
| MFA | TOTP (app-based) or WebAuthn. Avoid SMS if possible |
| Session ID | 128+ bits from `crypto.randomBytes()` |
| Session cookie | HttpOnly; Secure; SameSite=Lax |
| Session fixation | Regenerate ID on login, privilege change, logout |
| Absolute timeout | 12-24 hours max session lifetime |
| Idle timeout | 15-30 minutes of inactivity |
| Logout | Invalidate server-side session, clear cookie |
| Rate limiting | 5 attempts per account, escalating delays |
| Breached passwords | Check against Have I Been Pwned API |
| User enumeration | Same error message regardless ("Invalid username or password") |

## Misconception

**Myth:** "JWTs are always more secure than server-side sessions."

**Reality:** JWTs are a trade-off, not an upgrade. They provide statelessness at the cost of revocation difficulty, token size, and implementation complexity. A JWT with the `alg: "none"` vulnerability is trivially broken. A JWT with secrets in the payload leaks data to anyone who base64-decodes it (the payload is encoded, not encrypted). Server-side sessions with HttpOnly cookies are simpler and at least as secure for browser-based applications. Use JWTs where their properties (statelessness, cross-service portability) add value — not because they're "modern."
